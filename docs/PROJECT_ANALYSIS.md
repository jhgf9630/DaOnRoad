# DaOnRoad 프로젝트 분석

분석일: 2026-09-13 · 기준 커밋: `0752de5` (`update 25`, 2026-03-22)

## 1. 프로젝트의 목적과 범위

DaOnRoad는 승객 명단을 Excel로 받아 여러 버스에 배정하고, 각 버스의 방문 순서와 탑승 시각을 계산하는 데스크톱 프로그램이다. 차량마다 다른 출발지를 지정할 수 있지만, 모든 차량의 최종 도착지와 도착 목표 시각은 하나로 통일된다.

사용 흐름은 다음과 같다.

1. 이름·탑승 주소·인원이 있는 Excel 업로드
2. 주소를 좌표로 변환하고 지도에서 확인
3. 버스 ID·정원·출발지 등록 및 수정
4. 공통 도착지·도착 목표 시각 설정
5. 차량별 승객 배정 및 방문 순서 계산
6. 지도와 상세 목록에서 노선·탑승시간 확인
7. 3개 시트로 구성된 Excel 저장

현재는 회원·로그인·운행 이력·서버 DB가 없는 단일 사용자 중심 구조다. 승객·차량·결과는 화면 메모리에만 보관된다. 프로그램을 다시 열어 이전 작업을 복구하는 기능은 없다. API 요청에도 프로젝트나 작업 ID가 없다.

Excel 한 행은 한 명이 아니라 `passenger_count`명이 함께 이동하는 **분할 불가능한 그룹**이다. 화면 일부는 행 수를 '명'으로 표현하지만 실제 정원 계산은 인원 합계를 사용한다.

## 2. 조사 범위와 검증 한계

직접 작성된 Python 18개 파일(빈 패키지 초기화 파일 포함), Electron 메인 코드, 1,090줄의 HTML/CSS/JavaScript, README, 의존성 명세와 잠금 파일, Docker 설정, 실행·빌드 스크립트, 숨김 설정 파일을 조사했다. 별도의 AGENTS.md나 자동화 테스트·CI 설정은 발견하지 못했다.

지도 바이너리·아이콘·배포 실행파일·컴파일 캐시·외부 패키지는 소스 코드와 구분했다. 지도 데이터는 파일 구성, 캐시는 구조와 항목 수, 기존 배포본은 리소스 구성과 빌드 설정을 확인했다. 지도 바이너리의 도로망 품질이나 외부 라이브러리 전체 소스를 감사한 것은 아니다. 실제 API 키 값과 캐시의 주소는 이 문서에 기록하지 않는다.

실행 검증:

- Python 소스 18개: AST 문법 검사 통과
- Electron 메인 코드와 HTML 내부 JavaScript: 문법 검사 통과
- 외부 API를 호출하지 않는 Greedy 배차 및 시간 역산 사례 실행
- Compose 주소에 대한 OSRM 로컬 서버 판별 실행

현재 기본 Python은 3.10.11이며 FastAPI·pandas·openpyxl·OR-Tools가 설치되어 있지 않다. 따라서 OR-Tools 실제 최적화, Docker 전체 실행, 화면 조작, Excel 입출력, 실제 Kakao/OSRM 응답, 신규 배포 빌드는 검증하지 않았다. 분석을 위해 패키지를 설치하거나 기존 앱·컨테이너를 기동하지 않았다. 실제 서비스 코드 변경도 하지 않았다.

## 4. 데이터와 처리 흐름

### 업로드

`POST /api/upload`는 `.xlsx`와 `.xls` 확장자를 허용한다. `name`, `address`, `passenger_count`가 필수이며 이름/성명, 주소/탑승지, 인원/탑승인원/명 컬럼을 매핑한다. 이름·주소가 빈 행은 제거하고, 인원이 없으면 1로 채운 후 정수로 변환한다.

각 주소는 순차 검색하며 가장 먼저 반환된 후보를 자동 선택한다. 이름·주소·인원·좌표·변환 성공 여부를 응답한다. 화면은 좌표 변환에 성공한 행만 실제 배차 상태에 보관한다. 실패 행은 미리보기에는 나타나지만 수정·재검색하는 전용 기능은 없다.

### 주소 검색

Kakao 주소 검색 → Kakao 장소 검색 → Tmap 보완 순서다. 검색 결과는 `search:검색어:결과수` 키로 캐시한다. UI의 차량 출발지와 도착지는 후보를 사용자가 선택하지만, 승객 업로드에는 같은 확인 단계가 없다.

### 행렬과 배차

승객 행 수를 P, 차량 수를 V라고 하면 현재 실제 노드 수는 **P + 1 + 2V**다. 승객, 공통 도착지, 각 차량의 출발지, 각 차량의 종료지 복제 노드가 추가된다.

OSRM 환경변수가 있으면 Table API에서 초 단위 이동시간 행렬을 얻고, 실패하면 Haversine으로 전환한다. Haversine은 직선거리 × 1.3 / 시속 40km이며, 다른 노드 간 시간은 최소 60초다. 실제 거리 최소화라기보다 **예상 이동시간 비용 최소화**다.

OR-Tools가 있으면 차량별 정원을 가진 CVRP를 20초 탐색한다. 해가 없거나 라이브러리가 없으면 좌표 기반 K-Means → 정원 조정 → 가까운 지점 우선 방문 → 미배정 승객 보완으로 처리한다. 모든 버스를 쓰려는 후처리도 있다.

도착 목표 시각은 배차 최적화의 제약으로 사용되지 않는다. 배차가 끝난 후 시간표만 역산한다. 차량별 최대 운행시간, 승객 최대 탑승시간, 출발 가능 시각, 실시간 교통, 버스별 통행 제한, 정류장 통합, 복귀 운행, 수동 배차 고정은 현재 구현되어 있지 않다.

### 시간과 출력

선택된 인접 정류장 사이에 OSRM Route API로 지도 경로를 가져온다. 실패 구간은 직선으로 표시한다. 탑승 행마다 120초를 추가해 공통 도착 시각에서 역산한다. 같은 주소 여러 행도 별도 픽업·대기시간으로 처리한다.

결과는 `routes`, `destination`, `summary`, `matrix_source`로 반환된다. 각 route에는 차량 정보, 정류장, 인원 합계, 구간 좌표, 출발/도착 시각, 총 소요시간이 들어간다. 화면의 버스 탭은 다른 버스 선을 흐리게 할 뿐 마커를 함께 필터링하지 않는다.

Excel 저장은 결과 JSON을 다시 서버에 보내 3개 시트를 만들고, Electron 저장 대화상자로 파일을 저장하는 방식이다. 시각은 날짜 정보 없는 문자열이다.

## 6. 확인된 문제와 업그레이드 영향

### 우선: 배차 결과의 완전성과 정원

**미배정 승객이 있어도 성공으로 반환한다.** OR-Tools의 `AddDisjunction`은 높은 벌점을 주지만 방문을 필수로 만들지는 않는다. Greedy도 끝까지 넣지 못한 승객을 오류로 돌려주지 않는다. 최종 결과에 모든 입력 행이 정확히 한 번 포함되는지 검사하지 않는다. 응답 summary는 실제 배정량이 아니라 입력 인원 합계를 사용한다.

재현: 6명짜리 한 행, 정원 5명 버스 2대 → Greedy 결과 `success=true`, 실제 배정 0명. 총 정원은 10이어서 현재 화면의 총량 검사도 이 입력을 막지 못한다.

**빈 차량 강제 배정이 정원을 검사하지 않는다.** `_force_min_one`은 인원 1명을 쪼개 옮기는 것이 아니라 마지막 픽업 그룹 전체를 이동한다. 받는 버스 정원, 주는 버스의 남은 픽업 수, 기존 최적화 품질을 보장하지 않는다. 그룹 수가 차량 수보다 적으면 모든 버스에 배정하는 원칙 자체가 불가능하다. `_balance_clusters`도 이동받는 클러스터의 목록과 인원 합계를 같은 반복 안에서 일관되게 갱신하지 않는다.

재현: 정원 10인 A 차량에 2명·6명 그룹을 배정하고 정원 2인 B 차량을 비워 둔 채 후처리 실행 → A 2명, B 6명으로 반환되어 B의 정원을 초과했다.

**불필요한 종료 노드가 최적화에 포함된다.** MatrixBuilder가 각 차량의 종료지 노드를 만들지만 OR-Tools는 공통 도착지 인덱스만 종료점으로 사용한다. 추가 종료 노드들은 일반 노드로 모델에 남고 `_map_stops`에서 표시되지 않는다. 계산 비용·경로·표시 간 차이를 만들 수 있으므로 모델을 단순화해야 한다. OR-Tools 실행 검증은 후속 작업으로 남는다.

### 우선: 시간표 의미

**`departure_time`은 실제 차고지 출발시각이 아니라 첫 픽업 시각이다.** 총 소요시간에는 차고지→첫 픽업 구간이 포함되므로 요약이 서로 맞지 않는다.

재현: 출발지→픽업 10분, 픽업→도착지 10분, 탑승 대기 2분, 10:00 도착 → 출발 정류장 09:38, 요약 출발 09:48, 총 소요 22분.

자정을 넘는 역산은 날짜를 버린 채 `HH:MM`만 남는다. 화면은 최초 출발을 문자열 비교로 선택하기 때문에 전날 출발을 제대로 해석하지 못한다. 운행일·전날 표시·초 단위 반올림 규칙도 필요하다.

### 우선: 실제 확인된 보안·설정 문제

- `backend/.env`가 `.gitignore` 규칙과 달리 **Git 추적 중**이다. 키 설정도 존재한다. 캐시·pyc·OSM 원본·샘플 Excel도 이미 추적되어 있다. ignore 규칙 추가만으로 기존 추적이 해제되지는 않는다. 저장소 공개 여부와 외부 노출 범위는 이번 조사에서 확인하지 않았다.
- Electron은 `nodeIntegration: true`, `contextIsolation: false`, `webSecurity: false`로 설정되어 있다. 동시에 외부 CDN 스크립트와 입력값의 직접 HTML 삽입을 사용한다. 승객 이름·주소·버스 ID·검색 결과가 HTML/이벤트 속성으로 들어가는 지점이 많아 입력 데이터가 코드로 해석될 위험이 있다.
- 백엔드는 인증 없이 모든 Origin을 허용하며 Docker 포트도 호스트 루프백에 한정하지 않는다. 진단 API와 로그는 키 접두부를 노출한다. 실제 외부 접근 가능성은 호스트 네트워크·방화벽에 따라 달라진다.
- Windows 배포 스크립트는 `.env`를 배포 폴더에 복사한다. 사용자별 키와 배포·운영 자격증명 방식을 정리해야 한다.

### 배포와 실행

- 현재 `frontend/package.json`은 추가 리소스에서 `Dockerfile`을 제외하지만 배포된 Compose는 그것으로 백엔드를 빌드한다. `build.bat`은 지도와 `.env`만 추가하므로 **현재 설정으로 새 배포를 만들면 필요한 Dockerfile이 빠진다.** 기존 `dist/win-unpacked`에는 Dockerfile이 있고 저장된 빌드 설정도 현재와 다르다. 기존 성공 여부를 새 빌드의 근거로 삼을 수 없다.
- `build.sh`는 없는 npm script `build:mac`을 호출한다. 실제 이름은 `buildmac`이다. Windows와 Mac의 리소스 전달 방식도 통일되어 있지 않다.
- Windows portable exe 생성 후에 `win-unpacked`에 지도·설정을 복사하므로, portable exe 자체와 최종 폴더/ZIP을 같은 배포물로 보면 안 된다.
- `start.*`의 백엔드 대기는 종료 시한이 없다. OSRM healthcheck의 `|| exit 0`은 실패도 성공 처리한다. backend health는 OSRM 준비 여부를 검사하지 않는다.
- 앱 종료 시 Compose stop을 실행하고, 매 실행 시 `up -d --build`한다. Mac에서 모든 창을 닫은 뒤 다시 활성화할 때는 창만 열고 컨테이너 재시작은 하지 않는다.
- 지도 JS/CSS는 unpkg, 지도 타일은 OpenStreetMap에 의존한다. 로컬 OSRM 지도가 있어도 완전한 오프라인 앱은 아니다.
- `.xls` 입력을 안내하고 허용하지만 requirements에는 해당 형식의 읽기 엔진인 `xlrd`가 없다. 깨끗한 선언 환경의 `.xls` 지원은 확인이 필요하다.
- 추적 중인 대형 OSM 원본은 Docker 빌드 및 백엔드 추가 리소스 제외 목록에도 없다. 빌드·배포 용량을 불필요하게 키울 수 있다.

### 성능·장애 대응·캐시

- `async def` API 안에서 동기 HTTP 요청, pandas 처리, 파일 저장, 최적화, sleep을 실행한다. 단일 서버 프로세스의 이벤트 루프가 막혀 계산 중 health·검색 요청까지 지연될 수 있다.
- UI 제한은 업로드 30초, 주소 검색 8초, 노선 생성 90초다. 서버의 순차 주소 검색·재시도·구간별 경로 조회 시간은 이 한도를 넘을 수 있다. 화면 요청 중단은 서버 계산 취소가 아니다.
- `_is_local()`은 `http://osrm:5000`을 로컬로 인식하지 않는다. 직접 호출 결과 False였다. Compose 내부 서버에도 공용 서버용 대기와 청크 분기 규칙을 적용한다.
- 청크 처리는 sources 행만 나누며 전체 좌표·목적지는 매번 보낸다. 좌표 수·응답 크기 제한 회피를 보장하지 않는다. 코드의 '로컬 제한 없음' 주석은 서버 실제 설정 검증으로 대체해야 한다.
- 행렬 캐시 키가 Python `hash()`에 의존하여 프로세스 재시작 후 안정적이지 않다. 좌표 반올림 외에 서버·지도 버전도 반영하지 않는다.
- 캐시는 만료·원자적 저장·동시 접근 조정이 없다. 업로드와 routing은 별도 Geocoder 객체가 같은 파일을 읽어 메모리에 유지하므로 오래된 값 덮어쓰기와 초기화 불일치가 생길 수 있다.
- `DELETE /api/cache`는 거리/경로/행렬 전체 캐시 삭제가 아니다. upload 쪽 메모리 캐시도 함께 초기화하지 않는다.
- OSRM 도달 불가 셀을 직선 시간으로 보완하고도 전체 소스를 `osrm`으로 표시한다. 경로 좌표 일부가 직선으로 대체되어도 화면의 도로 경로 안내에 구간별 품질이 드러나지 않는다.

### 화면 상태·입력 검증

- 주소를 선택한 후 텍스트를 다른 비어 있지 않은 문자열로 수정하면 이전 `selected` 좌표가 유지된다. 새 검색 후보를 선택하지 않고도 이전 위치가 사용될 수 있다. 검색 응답 순서 역전 방지도 없다.
- 승객 재업로드나 차량·도착지 수정 시 기존 결과를 무효화하지 않는다. 화면 입력과 저장할 결과가 서로 다른 상태가 될 수 있다.
- 서버 모델은 인원·정원의 양수 여부, 좌표 범위, 차량 ID 중복, 빈 목록, 시간 형식을 충분히 제한하지 않는다. 출발지 검색 실패 시 오류 대신 도착지로 대체한다.
- 진행률과 처리 단계는 실제 서버 진행 상황이 아니라 화면의 고정 지연으로 표시된다.
- `innerHTML` 및 inline 이벤트가 많고, 주소 검색 객체를 다시 만들 때 document 클릭 리스너를 해제하지 않는다. 컴포넌트 분리 시 상태·이벤트 수명 관리가 필요하다.

## 7. 업그레이드 작업 순서 제안

1. **결과 정확성 기준 확정:** 모든 그룹 정확히 1회 배정, 정원 준수, 미배정 사유 명시, 차량 출발·첫 탑승시간 분리. 합성 입력으로 회귀 검사를 만든다.
2. **실행·배포 기준 정리:** 현재 설정으로 재현 가능한 빌드, Dockerfile 및 지도 리소스 포함, OSRM 준비 확인, 설정과 키 관리 정리.
3. **입력·화면 신뢰성 보완:** 좌표 실패 수정, 주소 변경 시 선택 무효화, 설정 변경 시 결과 무효화, 결과와 입력 인원 대조.
4. **구조 개선:** 화면 CSS/상태/API/지도 분리, Electron preload와 제한된 IPC, 서버 입력/결과 모델, 작업 실행·상태·취소 처리, 안정적인 캐시.
5. **실제 운영 조건 반영:** 최대 탑승시간, 사용 차량 수 정책, 같은 탑승지 통합, 수동 배차, 운행일·이력·재사용 등 필요 기능 확장.

이 순서는 현재 코드에서 확인한 정확성·배포 문제에 근거한다. 새로운 프레임워크나 제품으로 전면 교체해야 한다는 뜻은 아니다.

## 8. 후속 요구사항을 받을 때 확인할 정책

- 등록된 버스를 모두 운행해야 하는지, 필요한 차량만 선택할지
- 한 Excel 행의 그룹을 여러 버스로 나눌 수 있는지
- 목표가 총 이동시간, 가장 늦게 출발하는 시간, 최대 승객 탑승시간, 차량 수 중 무엇인지
- 차고지→첫 탑승지 이동도 운행 계획에 포함할지
- 같은 주소를 하나의 정류장으로 묶을지, 탑승 대기시간을 어떻게 정할지
- 실제 승객·차량 규모와 Windows/Mac 사용 범위
- 단일 PC 중심인지, 여러 담당자가 운행 기록을 공유해야 하는지

이번 단계에서는 위 정책을 임의로 바꾸지 않았다. 다음 업그레이드 요구를 이 구조·검증 결과와 연결해 구현할 수 있다.
