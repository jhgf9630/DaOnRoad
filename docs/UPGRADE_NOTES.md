# 배차 및 안정성 개선 기록

작성: 2026-09-14. 기존 코드 기준 커밋: `0752de5`.

## 적용한 운영 조건

사용자 확인값은 학생 약 500명, 예시 차량 21인승 10대·35인승 5대·45인승 5대, 편도 학생 탑승 최대 90분, Excel 행당 대기 120초다. 학생과 차량의 수·정원은 입력에 따라 바뀐다.

균형형 목표를 적용했다. 비용 정보가 없으므로 실제 요금 대신 총 차량 운행시간, 차량 사용 부담, 학생 전체 탑승시간을 합산한다. 초기 가중치는 아래와 같으며 화면에서 조정할 수 있다.

`목적값 / 100 = 차량 운행 초 합계 + 사용 차량 수 × 1,800초 + 학생별 탑승 초 합계 × 0.2`

차량 최대 운행시간은 출발지 이동을 포함해 240분, 탐색은 기본 60초다. 여러 인원이 있는 한 행은 분할하지 않고, 필요 차량만 사용한다. 전체 차량 사용은 선택 사항이다. 이 세 가지는 설정 가능한 구현 기본값이며 사용자가 확정한 고정 운영 정책으로 간주하지 않는다.

## 알고리즘

1. 도로 이동시간의 방향성을 유지하는 OSRM 행렬을 만든다. 중복 종료 노드를 없앴다.
2. 학생 인원·총 정원·그룹 정원·노드 구조·입력값을 검증한다.
3. 여러 지리적 분할에서 실제 도로 비용으로 방문 순서를 개선한 초기 후보와, 큰 그룹/원거리 그룹부터 삽입하는 후보를 준비한다. 단순 지리 클러스터 결과를 배차 완료로 간주하지 않는다.
4. OR-Tools에서 공통 도착지부터 차량 출발지로 거꾸로 탐색한다. 방향별 도로 시간은 뒤집어 참조하며, 역방향 픽업 누적시간이 실제 정방향 학생 탑승시간과 일치하도록 행당 대기를 넣는다.
5. 차량 정원, 필수 방문, 차량 운행시간, 학생 최대 탑승시간을 적용해 탐색한다. 학생 누락 벌점이나 빈 버스 강제 이동은 제거했다.
6. 초기 배정이 어려우면 시간 초과에 높은 벌점을 준 내부 보완 탐색도 사용한다. 이 내부 후보가 90분을 초과한 채 사용자에게 운행 결과로 반환되지는 않는다.
7. 결과를 별도 계산기로 다시 검증한다. 모든 입력 행이 정확히 한 번 포함되고 정원·운행시간·학생 탑승시간을 지킨 후보만 반환한다. 실패하면 명확한 오류를 반환한다.

행렬 비용은 C++ 엔진에 직접 등록하여 500명 규모에서 Python 비용 콜백을 반복하는 부담을 줄였다. 후보들의 목적값을 비교하며, 전역 최적성은 증명하지 않는다. 시간 제한·초기 후보 구성에 따라 결과가 달라질 수 있다.

구현 기반 API 참고: [OR-Tools Dimensions](https://developers.google.com/optimization/routing/dimensions), [OSRM Table/Route API](https://project-osrm.org/docs/v5.24.0/api/). 가중치와 위 탐색 구성은 DaOnRoad에 적용한 설계다.

## 결과 검증

### 이전/이후 동일 입력 비교

500명, 20대, 행당 120초, 각 탐색 20초. 약 8km 안팎의 비교적 좁은 가상 영역에 분산한 합성 좌표 및 방향별 예상시간 행렬이다. **실제 수도권 전체 도로 테스트가 아니다.** 기존 solver에도 수정된 동일 노드 구성을 제공해 비교했다.

| 지표 | 기존 배차 | 개선 배차 |
|---|---:|---:|
| 배정 학생 | 500 | 500 |
| 운행 차량 | 20 | 20 |
| 평균 탑승 | 47.36분 | 36.07분 |
| 최장 탑승 | 131.67분 | 81.52분 |
| 90분 초과 학생 | 61 | 0 |
| 총 차량 운행 | 1,400.17분 | 1,391.10분 |
| 정원 초과 | 0 | 0 |

평균 탑승시간 약 23.8% 감소, 총 차량 운행시간 약 0.6% 감소다. 원본 실행 결과는 [solver-comparison.json](solver-comparison.json), 재현 스크립트는 `scripts/compare_routing.py`다. 탐색이 시간 제한 방식이므로 재실행 시 수치는 조금 달라질 수 있다.

### 넓은 분산 사례

약 50~60km 범위에 500명을 고르게 분산시킨 합성 사례에서는 같은 20대·90분·행당 2분 조건을 만족하는 결과를 찾지 못했다. [benchmark-500.json](benchmark-500.json)에 실패도 남겼다. 이 결과는 **수학적 불가능의 증명도, 실제 500명 노선의 운행 가능성 판정도 아니다.** 알고리즘만 바꿔 임의의 학생 분포를 항상 90분 이내로 만들 수 있다고 주장하지 않는다. 실제 학생 주소와 차고지로 추가 보정·검증이 필요하다.

### 실제 도로 연동

사용자 PC의 기존 로컬 OSRM을 읽기 전용으로 사용해 가상 좌표 12명의 생성→경로 좌표→시간표→Excel을 확인했다. 12명 전원 배정, 1대 사용, 최장 탑승 41.4분, Excel 3개 시트 생성에 성공했다. API 키나 실제 학생 자료를 테스트에 사용하지 않았다. [road-integration.json](road-integration.json)

- Windows 패키지 빌드 및 Docker 이미지 빌드 확인. 일회용 컨테이너에서 백엔드 로딩 및 기존 로컬 OSRM readiness 확인.
- 프런트엔드 설치 후 npm 보안 검사: 보고된 취약점 0개. 전체 시스템에 취약점이 없다는 의미는 아니다.
- Python 테스트 도구에서는 httpx/anyio 관련 폐기 예정 API 경고 2개가 남는다. 테스트 실패는 없다.
- Mac 실행, 실제 500명 학생 주소, 실제 운행/실시간 교통, 완전한 오프라인 실행은 검증하지 않았다.

## 함께 수정한 문제

- 차고지 출발시간과 첫 탑승시간 분리, 운행일/전날 표시, 정확한 초 단위 계산.
- Excel 행 누락·음수·소수 검증. `.xls` 엔진 추가. 주소 변환 실패 행이 있으면 배차 차단.
- 실제 단계별 진행 조회, 서버 작업 ID, 취소, 단일 배차 실행 제한. API 계산 중 health 요청이 막히는 구조 개선.
- 주소 텍스트 수정 시 과거 좌표 해제, 검색 응답 순서 역전 방지, 이벤트 리스너 정리, 조건 변경 시 기존 결과 무효화.
- OSRM 청크를 행·열 양쪽으로 분할. 도달 불가 구간은 가짜 직선 이동으로 연결하지 않음.
- 도로 서버 실패 시 기본적으로 계산 중단. 사용자가 명시적으로 허용해야 추정 계산. 지도 직선 구간 별도 표시.
- 캐시의 안정적 해시, 만료, 파일 원자적 저장, 스레드 간 공유·잠금, 전체 캐시 초기화.
- Electron Node 접근 차단, 문맥 분리 및 sandbox, 제한된 저장 IPC, 외부 탐색 차단, 입력 HTML 이스케이프, 외부 CDN 코드 제거.
- API 키 접두부 진단/로그 제거, 로컬 포트 바인딩, 출처/앱 헤더 검사, 최신 웹/업로드·Electron 의존성 적용.
- Dockerfile 패키징 누락 해결, 대형 지도 원본/캐시/개발 키의 패키징 제외, Mac 명령 이름 수정, 실행 대기 시한, 실제 도로 readiness.
- 이전 버전 백엔드가 포트를 점유한 경우 새 UI에서 버전 불일치를 표시.

## 적용 및 남은 운영 작업

소스와 검증용 산출물을 수정했으며, 실행 중이던 기존 배포 서비스는 중지하거나 교체하지 않았다. 실제 사용 시 기존 앱을 종료하고 README의 개발 실행 또는 재빌드 절차를 따른다. 검증 폴더는 완성된 지도 포함 배포 ZIP이 아니다.

`.env`, 캐시, pyc, 대형 지도 원본은 **파일을 삭제하지 않고 Git 추적만 해제**했다. 키 값은 이번 작업의 문서/새 배포본에 넣지 않았다. 기존 Git 이력에 남아 있는 키는 그대로이므로 외부에 공유한 적이 있다면 키 재발급이 필요하다. 저장소 이력의 강제 재작성은 하지 않았다.

향후 실제 차량별 고정요금/시간당 운행비가 제공되면 현재의 환산 비용을 실제 비용 모델로 바꿀 수 있다. 실데이터 적용 전에는 실제 승객 위치·차량 출발지·도로 시간·탑승 대기를 함께 확인해야 한다.
